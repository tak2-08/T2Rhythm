# T2Rhythm 전용 실행기와 기능 패키지 검토

갱신일: 2026-10-24. 이 문서는 현재 네이티브 앱을 유지하는 전환 설계와 단계별 구현 현황이다. 배포된 1326은 아직 기존 APK 구조를 사용한다.

## 질답으로 확정한 사용 경험

- **현재 T2Rhythm 자체를 베이스 앱으로 전환한다.** 별도 런처나 앱 선택 화면을 만들지 않으며, 아이콘을 누르면 지금처럼 바로 음악 앱을 연다. 기존 앱 ID와 배포 서명을 유지하는 한 번의 베이스 APK 갱신으로 보관함·설정·허용된 권한을 이어간다.
- 첫 실행용 음악 기능을 내장 기본 패키지로 포함한다. 최초 다운로드 없이도 오프라인으로 사용하고, 복구 시에도 사용한다. Android 8(API26) 이상 지원을 유지한다.
- 기능 패키지는 사용자가 설치를 선택하고 적용을 확인한 뒤 **다음 안전한 앱 시작**에 반영한다. 적용 확인 전에 새 코드를 로딩하거나 실행하지 않는다. 백그라운드 재생·공유·작업이 살아 있는 상태에서 Activity를 다시 여는 것은 적용 시점이 아니다. 프로세스마다 하나의 기능 버전을 고정한다.
- 음악 접근 등 필수 권한을 먼저 안내하고, 카메라·Bluetooth·위치·마이크는 해당 기능을 처음 사용할 때 요청한다. 모든 권한을 최초 실행에서 일괄 요구하지 않는다. OS에 의한 권한 취소·자동 초기화 시에는 다시 확인한다.
- 기존 Kotlin/Compose 화면·디자인·기능을 유지한다. 베이스 앱을 최초 설치하거나 실제로 교체할 때의 Android 설치 확인, 새로운 권한·페어링·MediaStore 파일 수정 동의는 그대로 필요하다. 평소 기능 패키지 설치에는 Android 패키지 설치기를 사용하지 않는다.

## 현재 구현 범위

별도 `:runtime-core` 모듈에 서명된 패키지 검증과 적용 상태 전이 규칙을 구현했다. 패키지 형식과 검증 경계는 [기능 패키지 v1](runtime/PACKAGE_FORMAT_V1.md)에 기록한다.

- 고정된 공개키로 원문 manifest 서명을 확인한 뒤 페이로드·변경 내역의 해시/크기를 확인한다. APK 버전·host API·공유 런타임 지문·Android 버전·DB 스키마와 맞지 않는 패키지를 거부한다.
- 서명된 내용에 변경 내역을 포함하며, 승인 대상을 정확한 아카이브 SHA-256에 묶는다. 새 후보로 교체하면 이전 승인을 이어받지 않는다.
- 사용자 확인·안전한 프로세스 시작을 함께 요구하며, 새 버전 첫 부팅 완료 전에는 이전 정상 버전을 보존한다. 시험 부팅이 끝나지 않았으면 다음 프로세스에서 복구를 결정한다. DB나 최소 허용 버전이 맞지 않는 구버전은 자동 실행하지 않는다.

실제 Android 로딩을 확인하기 위한 시험 경로도 분리했다. `:runtime-api`의 네이티브 View 인터페이스, `:runtime-host`의 읽기 전용 DEX 시험 로더, `:runtime-probe`의 독립 빌드 Compose 화면과 Android instrumentation 검사다. 시험 화면은 새로운 앱 디자인이 아니라 별도 DEX의 실행·클릭을 확인하는 fixture다. 시험 로더는 앱 전용 no-backup 경로의 불변 아카이브를 다시 검증하고, 정확한 적용 승인 결과와 비교한 뒤 읽기 전용 DEX만 로딩한다. 라이브러리 복사본을 DEX에 넣지 않는다.

이 단계에는 **원자적 상태 저장, 내장 기본 모듈 분리, 기존 앱 전체의 원격 모듈 실행, 네트워크 배포/UI 연결이 아직 없다.** `:app`의 런타임 경로는 어떤 모듈도 의존하거나 호출하지 않는다. `androidTestImplementation`과 테스트 전용 생성 자산에만 연결했다. JVM 테스트는 패키지 검증·정책의 증거이며, 시험 화면의 실행도 기존 앱 전체의 동일 동작을 보증하지 않는다. 기존 1326을 이 설계의 완성본으로 배포하지 않는다.

이 실험 뒤 기존 코드를 사용하는 화면을 모듈로 옮겨 기본 구현과 같은 데이터·테마·가로 화면·글씨 크기에서 비교한다. Android 26의 리소스 전달과 R8을 적용한 독립 빌드 조합까지 확인한 뒤 전체 앱의 경계를 옮긴다.

## 결론

가능하다. **한 번 설치한 실행기 APK + T2Rhythm 전용으로 빌드하고 서명한 기능 패키지**로 나누면, 실행기가 기능 패키지를 내부 저장소에 보관하고 그 코드를 실행할 수 있다. 일반 기능 업데이트마다 Android 패키지 설치기를 호출할 필요는 없다. 웹 화면이나 WebView로 바꿀 이유도 없다. Kotlin/Compose로 작성한 기존 화면과 로직을 재사용하는 방식을 우선한다.

하지만 현재 배포 APK를 그대로 받아 `DexClassLoader`로 열기만 해서 앱 전체가 동일하게 실행되는 것은 아니다. DEX 로딩은 클래스 로딩이며 APK의 AndroidManifest, Activity, 서비스, 수신기, Provider, 권한, 리소스를 새 앱처럼 등록하는 설치 작업이 아니다. 이 차이를 해결하려면 빌드 모듈과 앱의 진입점을 분리해야 한다. 파일 확장자를 바꾸거나 설치 경고를 숨기는 방식으로 해결되지 않는다.

## 사용자가 요청한 업데이트 경험

1. 업데이트 화면에서 버전·변경 내용·용량·실행기 호환 여부를 표시한다.
2. 사용자가 **설치**를 누르면 해당 릴리스의 기능 패키지를 다운로드하고 서명·해시·호환성을 검증한다. 저장소 최신 소스를 임의로 실행하지 않는다.
3. 검증 후 **이 버전 적용 확인**에서 다시 확인한다. 취소하면 현재 버전을 계속 사용한다. 확인 전에는 새 기능 코드의 클래스 초기화나 실행도 하지 않는다.
4. 재생 중이면 즉시 프로세스를 재시작하지 않고 적용을 미룬다. 사용자에게 다음 실행 시 적용될 것임을 표시한다.
5. 다음 안전한 앱 시작에서 새 기능 패키지를 활성화한다. 다운로드 중단·오프라인·디스크 부족이면 기존 패키지로 계속 실행한다.
6. 새 버전 초기화에 실패하면 직전 정상 버전 또는 실행기에 내장한 기본 구현으로 복구한다. 사용자 데이터 호환성이 확보된 경우에만 자동 복구한다.

사용자 확인은 앱 안의 적용 동의다. Android 권한 허용·Bluetooth 페어링·실행기 APK의 실제 교체에 필요한 시스템 확인을 대신하지 않는다.

## 코드와 빌드 경계

| 부분 | 담당 | 업데이트 방식 |
| --- | --- | --- |
| 실행기 APK | AndroidManifest의 Activity·미디어/공유 서비스·알림·권한·Provider·Keystore·모듈 설치/복구·기본 구현 | 필요할 때 Android 설치 확인을 거쳐 APK 교체 |
| 고정된 host API | 앱 생명주기·재생 세션·저장소·권한 요청·UI 진입점의 명시적 인터페이스 | API 호환 범위를 실행기가 선언 |
| 서명된 기능 패키지 | 기존 Compose 화면과 기능 구현, 모듈 전용 리소스 | 사용자 확인 후 내부 저장·DEX 로딩 |
| 기능 패키지 manifest | 버전, host API/실행기 최소·최대 범위, 데이터 스키마 호환 범위, ABI, 파일 크기·해시, 서명 키 ID | 패키지와 함께 서명하여 배포 |

기존 Media3 서비스와 시스템 진입점은 실행기에 남기고 안정된 인터페이스를 통해 기능 코드를 호출한다. 다운로드한 APK의 Activity를 숨겨진 Android API로 등록하거나 기존 클래스 정의를 실행 중 덮어쓰는 방식은 사용하지 않는다. 기존 기능 구현을 모듈로 옮길 때 디자인을 다시 만드는 대신 원래 Compose 코드를 옮긴다.

Compose 컴파일러·Kotlin·라이브러리 버전은 host와 module 간 ABI가 일치해야 한다. 같은 클래스를 서로 다른 로더에 중복 제공하면 캐스팅·상태 복원에 실패할 수 있으므로 공용 타입과 런타임 라이브러리는 부모 로더에 둔다. R8이 인터페이스 이름·반사 진입점을 없애지 않게 빌드 규약을 고정하고, 독립적으로 빌드한 릴리스 조합을 검사한다.

리소스는 별도 문제다. API 30 이상은 공개 ResourcesLoader/ResourcesProvider 경로를 검토할 수 있지만, 현재 최소 API는 26이다. Android 8~10까지 유지하려면 실행기에 공통 Android 리소스를 남기고 모듈의 이미지·텍스트는 명시적 asset API로 제공하거나, 검증된 버전별 리소스 전달 계층을 구현해야 한다. hidden API `addAssetPath` 의존으로 호환성을 보장한다고 할 수 없다. 네이티브 라이브러리·JNI·ABI·16KB 정렬도 별도 검증 대상이며, 1차 전환에서는 실행기에 둔다.

## 패키지 배포와 검증

GitHub Actions에서 같은 소스로 실행기와 기능 패키지를 빌드한다. GitHub Releases의 특정 버전 아티팩트를 받으며, 브랜치의 변경 가능한 raw Kotlin 파일을 받아 폰에서 컴파일하는 방식은 선택하지 않는다. `.t2module` 같은 확장자는 포장 형식일 뿐 보안 기능이 아니다.

실행기에 고정한 공개키로 서명된 manifest와 패키지 내용을 검증한다. HTTPS와 같은 저장소에서 함께 받은 SHA256SUMS만으로 발행자를 인증할 수 없으므로 별도의 서명 검증이 필요하다. 모듈 키는 기존 APK 서명 키와 역할을 분리하고 오프라인 보관·회전·폐기 규약을 마련한다. 파일 크기·압축 해제 크기·경로·중복 ZIP 항목·ABI·API 범위·버전과 해시를 제한한다. URL 리디렉션이나 GitHub 계정 탈취만으로 새 코드를 승인할 수 없게 한다.

패키지는 외부 Download 폴더나 공유 캐시에 두지 않는다. 앱 전용 no-backup 영역에 정상/후보 슬롯을 별도로 두고, 열린 파일을 먼저 읽기 전용으로 만든 다음 그 descriptor로 쓰고 fsync 후 검증한다. 활성 슬롯은 원자적으로 바꾼다. Android 14 이상에서 동적 로딩 파일은 읽기 전용이어야 한다. 앱을 껐다 켜도 마지막 정상 패키지는 남으며, OS가 삭제할 수 있는 code cache는 재생성 가능한 최적화 결과만 보관한다.

동적 DEX 코드는 같은 앱 UID와 기존 권한으로 실행된다. 안전하게 제한된 스크립트 샌드박스가 아니므로 **T2Rhythm이 서명한 신뢰 코드만 허용**한다. 사용자 지정 저장소나 임의 APK 실행 기능은 포함하지 않는다.

## 기능 100% 유지의 판정

같은 소스를 재사용하는 것은 출발점이지 보증이 아니다. 기존 배포 APK와 실행기+모듈을 같은 데이터로 비교해야 한다. 최소 Android 26/29/30/35/37, 가로/큰 글씨/프로세스 재시작에서 다음을 통과하기 전에는 기존 설치 경로를 대체하지 않는다.

- 기존 화면·디자인·탐색·편집·장르·가사·온라인 다운로드·설정·접근성.
- 백그라운드 재생·잠금화면·MediaSession·Bluetooth 오디오·구간 탐색·알림·오디오 포커스.
- 로컬 스캔·MediaStore 쓰기 동의·Room·파일 참조·보관함·백업/복구·통계.
- LAN/Bluetooth 공유·인증서 핀·연결 승인/취소·오프라인 시작.
- 업데이트 다운로드 중단·후보 변조·키 변경·호환되지 않는 모듈·캐시 삭제·적용 중 강제 종료·복구.

데이터베이스 스키마를 올린 뒤 구버전 모듈로 돌아가면 데이터가 손상될 수 있다. 되돌릴 수 없는 migration은 모듈 활성화와 묶어 무조건 실행하지 않는다. 호환 스키마 범위와 데이터 보존 전략이 확인된 패키지만 전환한다. 불가역 스키마 변경은 실행기 업데이트 또는 명시적인 별도 전환으로 취급한다.

## 여전히 APK 업데이트가 필요한 경우

새 권한·새 Android 시스템 컴포넌트·foreground service 유형·host API·Compose/JNI 공용 런타임·OS 보안 변경은 실행기 교체가 필요할 수 있다. 따라서 ‘평소 기능 업데이트의 설치기 반복을 줄인다’는 목표는 가능하지만 ‘처음 설치 후 영원히 APK를 갱신하지 않는다’는 보장은 불가능하다. Play Protect를 끄거나 경고 표시를 우회하는 기능도 아니다.

현재 GitHub 배포판을 대상으로 검토한다. Google Play로 배포하려면 원격 실행 코드에 대한 별도 배포 정책 제약이 있다. 이 설계를 그대로 Play 배포 가능하다고 판단하면 안 된다.

## 권장 진행 순서

먼저 기존 APK와 동일한 화면을 로컬 내장 모듈로 분리하고 전체 회귀 검사를 통과시킨다. 다음으로 서명된 후보 패키지를 받아 **사용자 설치·적용 확인 → 다음 시작에서 활성화 → 실패 복구** 경로를 만든다. 마지막에 네트워크 배포와 버전별 호환성 검사를 연결한다. 패키지 다운로드만 먼저 연결하여 검증되지 않은 전체 앱 코드를 실행하는 전환은 하지 않는다.

- [Android 14 동적 로딩 파일 읽기 전용 요구사항](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading).
