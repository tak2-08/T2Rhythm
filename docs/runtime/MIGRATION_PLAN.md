# 기존 앱을 실행기 + 기본/갱신 기능 패키지로 옮기는 순서

2026-10-24. 이 문서는 다음 구현의 경계다. 현재 코드는 검증기·상태 기록·시험 로더·리소스 실험이며, 음악 앱 전체의 전환이나 배포 완료가 아니다.

## 확정한 사용자 경험

- 현재 앱 ID·배포 서명을 유지한 베이스 APK로 한 번 전환하고, 아이콘을 누르면 바로 기존 음악 화면을 연다.
- 기본 음악 기능을 내장하여 최초 실행·오프라인·복구를 지원한다.
- 기능 패키지는 사용자 설치 선택과 적용 확인을 거쳐 다음 안전한 시작에 반영한다. 재생·공유·작업을 끊거나 실행 중 클래스 버전을 교체하지 않는다.
- 선택 권한은 해당 기능을 처음 사용할 때 요청한다. Android 8 이상과 기존 디자인·기능을 유지한다.

## 다음 코드 경계

| 영역 | 남길 위치 | 이전할 구현 |
| --- | --- | --- |
| AndroidManifest와 시스템 진입점 | 베이스 | manifest 등록은 그대로 유지하고 실제 동작을 기능 패키지에 위임 |
| Application | 베이스의 최소 부팅·복구·WorkerFactory | 기존 초기화·작업 예약·이미지 로더 구성은 기능 구현으로 위임 |
| Main/External/Selector/Guard Activity | 베이스의 Activity·권한·생명주기 연결 | 기존 Compose/네이티브 화면과 이벤트 처리 |
| MediaLibraryService/공유 Service/TileService | 베이스의 시스템 서비스 객체 | 기존 세션 구성·재생 제어·공유·타일 로직 |
| 위젯 Receiver/아트워크 Provider | 베이스의 공개 시스템 주소 | 기존 위젯·아트워크 처리 |
| Worker | 베이스의 WorkerFactory | 기존 클래스 이름을 현재 기능 로더로 찾아 실행 |
| 기능/화면/ViewModel/Room 구현 | 기능 패키지 | 기존 소스를 재사용하며 데이터를 새로 만들거나 경로를 변경하지 않음 |
| Kotlin/Compose/Media3 등 공용 런타임과 JNI | 베이스 | ABI·버전·16KB 정렬·공용 리소스 ID 계약을 고정 |

실행기 시스템 컴포넌트는 공개 SDK로 직접 등록한 클래스다. 다운로드한 Activity를 숨겨진 `attach`/Instrumentation API로 등록하는 방식은 사용하지 않는다. Activity는 호스트 객체를 받은 명시적 delegate로 옮기고, 기존 생명주기 순서·인텐트·ActivityResult·ViewModelStore·SavedState를 보존한다. 음악 서비스도 알고리즘 전체가 베이스에 고정되는 실수를 피하고, 시스템 접점과 기능 구현을 나눈다.

Provider는 초기 생성만으로 UI보다 먼저 기능 버전을 고정하지 않도록 실제 요청 시점과 분리한다. WorkManager는 시스템 초기화 Provider가 Application보다 먼저 실행될 수 있음을 고려한다. 첫 실제 진입점에서 버전을 한 번 정하고, 이미 백그라운드 기능이 실행된 프로세스는 새 화면을 열어도 그 버전을 유지한다.

## 리소스와 ABI

시험 로더는 부모의 공용 타입을 먼저 사용하되, 기능 패키지의 `chromahub.rhythm.app.R*`/`BuildConfig`를 우선한다. 기존 APK에 없는 새 문자열이 부모 R 클래스에 가려지는 것을 막기 위한 예외다. `MusicViewModel` 등 실제 구현을 부모 DEX에 계속 두고 갱신됐다고 판단해서는 안 된다. 완성된 베이스에서는 공용 API/시스템 연결 외의 해당 클래스가 기능 로더에서 정의되는지 검사한다.

베이스의 라이브러리 R ID와 시스템 UI가 참조하는 리소스는 안정된 ID 목록으로 유지해야 한다. 현재의 일반 문자열/벡터·언어 시험만으로 테마·위젯 RemoteViews·공용 라이브러리 리소스까지 같다고 판단하지 않는다. 기본/새 기능의 독립 빌드와 프로덕션 R8 조합도 비교해야 한다.

공용 런타임 지문은 실제 빌드 입력에서 계산한다. Kotlin/Compose 도구, 공용 라이브러리/ABI, API 인터페이스, 안정된 리소스 ID 규약과 minifier 규약을 포함한다. 현재 기기 시험의 지문은 fixture용 값이며 배포용 계산기가 아니다. 라이브러리를 두 로더에서 서로 다른 이름·버전으로 실행하여 Activity/Compose/Media3 타입이 갈라지지 않도록 한다.

## 저장과 업데이트 연결

베이스는 신뢰하는 내장 패키지를 초기 정상 버전으로 준비한다. 설치된 버전·이전 정상 버전·후보는 앱 전용 no-backup 슬롯에서 관리한다. 다운로드 완료 파일의 검증, 사용자가 확인한 해시의 영속 기록, 안전한 시작에서 시험 상태의 영속 기록, 로딩과 실제 초기화 확인 순서를 지킨다. 프로세스가 살아 있는 동안 이전 버전을 추가로 로딩하여 복구하지 않는다.

현재 상태 저장소에는 기본 세대가 바뀌는 베이스 APK 갱신의 상태 이전, 슬롯 정리, 정상 버전 로딩/복구 UI를 연결해야 한다. 저장한 참조는 서명/무결성 검증과 현재 환경의 호환성 판정을 구분하여 처리한다. 호환되지 않는 후보 하나 때문에 정상 버전까지 버리지 않도록 한다. 데이터 스키마는 Room뿐 아니라 저장 파일·설정·복구 가능성도 포함한다. 불가역 변경을 자동 롤백과 함께 실행하지 않는다.

다운로드는 GitHub의 버전별 서명 패키지를 사용한다. 업데이트 화면은 기존 화면 안에서 변경 내역 → 설치 선택 → 적용 확인 → 다음 시작 적용 대기 → 적용/복구 결과를 제공한다. 실행기 교체가 필요한 경우에만 APK 설치 경로를 제시한다. 주요 버전 표시는 기능 버전으로 하고 실행기 버전은 상세 정보에서 구분한다. 기존 APK 전용 업데이트 사용자도 새 베이스로 전환할 수 있도록 릴리스의 APK 버전·자산·체크섬을 맞춰 제공한다.

배포용 모듈 키와 공개키 고정·회전·폐기, 패키지 서명/게시 자동화는 아직 연결하지 않았다. 시험 키는 실제 배포 신뢰 루트로 사용하지 않는다.

## 전체 전환의 완료 판정

현재 `:app`의 main 소스·manifest·리소스는 그대로이며 새 모듈 의존성은 instrumentation 전용이다. 이를 앱 전체가 모듈로 전환됐다는 증거로 사용하지 않는다. 다음을 확인하기 전에는 기존 설치 경로를 대체하거나 완성판으로 PR/배포하지 않는다.

- 실제 최초 베이스 전환에서 서명·앱 ID·기존 DB·음원 URI·설정·플레이리스트·대기열/재생 위치·가사/이미지·공유 인증 정보와 작업을 보존한다.
- 내장 기능과 외부 기능의 주요 클래스가 실제 기능 로더에서 실행되고, 새 빌드가 이전 구현에 가려지지 않는다.
- 원본 앱과 같은 데이터로 주요 화면·탐색·큰 글씨·가로 화면·접근성을 비교한다.
- 실제 재생·백그라운드/잠금화면·Bluetooth·위젯·파일 편집·다운로드·장르·가사·공유와 기존 회귀 검사를 통과한다.
- 사용자 확인 전 실행 없음, 재생 중 적용 연기, 다운로드 중단·변조·호환성 오류·강제 종료·상태 손상·오프라인 및 데이터 호환 복구를 확인한다.
- API26/29/30/35/37과 실제 minify된 베이스/독립 기능 패키지 조합을 검사한다. 기기별 검사나 화면 출력을 제공하지 않는 에뮬레이터의 한계는 구분하여 기록한다.
